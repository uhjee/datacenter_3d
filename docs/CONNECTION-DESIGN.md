# 연결관계 기능 설계 (DCIM 제품화 가정)

장비 간 관계를 사용자가 한 번만 설정하면, 아래 네 기능이 모두 그 설정에서 만들어지도록 연결관계 기능을 정의한다.

1. 전선 단선도
2. 공조 흐름도
3. 계통 관계
4. 우측 사이드 패널 > 연결

현재 시뮬레이션도 연결 데이터 하나에서 네 화면을 만든다. [connections.ts](../src/data/connections.ts)의 `CONNECTIONS`가 원천이고, 흐름도([model.ts](../src/diagram/model.ts)), 계통 묶음([groups.ts](../src/data/groups.ts)), 연결 패널([ConnPanel.tsx](../src/ui/ConnPanel.tsx))은 모두 여기서 계산한다. 제품화할 때도 이 방향은 유지한다. 바꿀 것은 세 가지다. 사용자가 직접 입력할 수 있게 하고, 입력을 검증하고, 지금 한데 섞여 있는 개념을 나눈다.

---

## 1. 핵심 원칙: 관계는 한 곳에만 저장하고, 기능 4개는 그 관계를 보는 화면이다

```
[L1 원천 · 사용자 입력]   장비 · 포트 · 연결          ← 최초 1회 설정 + 변경 관리
        ↓
[L2 그래프 엔진 · 계산]   상류/하류 추적 · 계통 전파 · 이중화 판정 · 묶음
        ↓
[L3 화면]  전선 단선도 │ 공조 흐름도 │ 계통 관계 │ 사이드 패널 > 연결
        ↑
[L4 화면 전용 데이터]  도면 좌표 · 묶음 규칙 · 색상   ← 관계와 따로 저장
```

화면마다 연결을 따로 그리는 일은 없어야 한다. 단선도에서 선을 하나 고치면 나머지 세 화면에도 바로 반영된다.

## 2. 개념 정의

| 개념 | 정의 | 현재 코드 |
|---|---|---|
| **인프라 타입** | 장비가 속한 분야: 전력 · 공조 · 방재 · 보안 · IT | `Domain` |
| **장비 유형** | UPS, PDU, 항온항습기 같은 유형. 인프라 타입과 **포트 템플릿**을 가진다 | `EquipType` (포트 없음) |
| **장비** | 실제 장비 한 대 | `EQUIPMENT` |
| **포트** ★ | 장비의 연결 지점. 방향(입력/출력), 매체, 역할을 가진다 | **없음** |
| **매체** | 연결로 흐르는 것: 특고압 AC, 저압 AC, DC, 냉매, 냉수, 냉각수, 연료 | `ConnKind`에 다른 개념과 섞여 있음 |
| **연결** | 출력 포트 → 입력 포트. 방향은 공급하는 쪽 → 받는 쪽 | `Conn` |
| **연결 지점** | 모선 · 헤더. 여러 장비가 다대다로 붙는 곳 | `HUBS` |
| **계통** | A · B 같은 경로 이름 | 연결마다 직접 입력 (`sys`) |

### 2.1 인프라 타입은 장비에, 매체는 연결에 붙인다

공조 동력반에서 냉동기로 가는 선은 전력 매체다. 그래서 이 선은 단선도에 나오고, 냉동기는 단선도에서 '부하'로 표시된다. 현재 `mech` 연결의 `domain: 'power'`가 이미 이렇게 동작하므로, 이 규칙을 정식으로 정한다.

### 2.2 포트를 도입한다

제품이 되려면 가장 먼저 필요한 것이 포트다. 포트가 없으면 다음을 알 수 없다.

- STS의 우선 입력과 대체 입력, UPS의 상용 입력 · 바이패스 · DC 입력 중 무엇이 끊겼는지
- 잘못된 연결 (예: UPS 출력을 다른 UPS 출력에 잇는 경우)
- 항온항습기의 전원 포트와 냉수 공급 · 환수 포트 구분

포트는 장비를 등록할 때 장비 유형의 템플릿에서 자동으로 만들어진다. 사용자가 따로 입력하지 않는다.

### 2.3 `ConnKind`를 매체 · 계통 · 역할로 나눈다

`upsA`, `upsB`, `sts`는 매체가 아니다. 매체(저압 AC)에 계통(A)과 출처 장비의 역할(UPS 출력)이 합쳐진 값이다. 제품에서는 매체만 저장하고, 계통과 역할은 계산한다.

- **계통은 소스 장비에만 지정하고 하류로 전파한다.** TR-A에 A를 달면 그 아래 ATS, UPS, PDU, 랙 회로가 모두 A가 된다.
- STS처럼 A와 B가 만나는 장비의 출력은 'A/B 선택'으로 계산한다.
- 이렇게 하면 사용자가 연결 수백 개에 A/B를 하나씩 붙이지 않아도 되고, 잘못 붙일 일도 없다.

## 3. 관계는 세 종류로 나눈다

모든 관계를 '연결' 하나에 담으면 금방 엉킨다.

| 관계 | 의미 | 예 | 쓰는 곳 |
|---|---|---|---|
| **공급** (물리 연결) | 전기나 유체가 실제로 흐른다. 방향이 있다 | UPS → PDU, 냉동기 → 냉수 헤더 | 단선도 · 흐름도 · 추적 |
| **담당** (논리) | 실제 선은 없지만 서비스를 제공한다 | 항온항습기 → 담당 구역 · 랙 (기류), 센서 → 구역 | 공조 흐름도의 공기 구간, 영향 분석 |
| **포함** (위치) | 어디에 있는지 | 서버실 ⊃ 랙 ⊃ rPDU | 3D 배치, 트리 |

공조 흐름도는 배관(냉매 · 냉수 · 냉각수)과 공기, 두 부분으로 이뤄진다. 배관은 공급 관계로 그리고, '항온항습기 → 랙'은 담당 관계로 이어 붙인다.

## 4. 데이터 구조 (DB 기준)

```
infra_domain   (code, name)                                   전력 · 공조 …
medium         (code, domain, name, color, is_pipe,
                supply_label, return_label)                   저압AC, 냉수(공급 7°C/환수 12°C) …
equip_type     (code, domain, name)
port_template  (type_code, port_code, dir[in|out|bi],
                medium, role[primary|alternate|bypass|dc|supply],
                max_links)                                    STS.in_pref, STS.in_alt, STS.out …
equipment      (id, type_code, name, location…, system_tag?)  system_tag는 소스 장비에만
port           (id, equipment_id, port_code)                  템플릿에서 자동 생성
link           (id, from_port, to_port, medium,
                normal_state[closed|open],                    open = 평상시 대기 경로 (점선)
                via, note, revision_id)
relation       (id, kind[serves|contains], from_id, to_id)    담당 · 포함
revision       (id, status[draft|published], author, at, memo)
view_layout    (view_id, node_id, x, y, collapsed)            도면 좌표. link와 분리
group_rule     (id, name, rule_json)                          계통 묶음 규칙
```

- **설계상 상태와 실시간 상태를 구분한다.** `link.normal_state`는 설계상 위상이다. ATS 절체나 차단기 개폐 같은 실제 상태는 감시 값에서 받아 그래프 엔진이 덮어쓴다. 현재 `scenario/` 폴더의 정전 · UPS 고장 시나리오도 같은 그래프 위에서 '전기가 어디까지 가는지'를 전파하는 계산으로 바꿀 수 있다.
- **배관은 공급과 환수를 연결 한 줄로 저장한다.** 두 줄로 나누는 것은 화면에서만 한다.
- 모선 · 헤더(연결 지점)는 가상 장비 유형(`bus`, `header`)으로 등록해 장비와 같은 방식으로 다룬다.

## 5. 최초 설정 UX

### 5.1 입력 방법 (현장에서 많이 쓸 순서)

1. **결선표 엑셀 가져오기.** 현장에는 이미 결선표나 판넬 스케줄이 있으므로 주력 입력 경로가 된다.
2. **규칙 템플릿.** 예: "서버실 A의 PDU-A1~9는 UPS-A1 출력에서", "냉각탑-n → 펌프-n → 냉동기-n". 현재 `connections.ts`의 반복문을 UI로 옮긴 것이다.
3. **도면에서 포트끼리 드래그.** 단선도나 흐름도 편집 모드에서 쓴다.
4. **사이드 패널에서 '상류 지정'.** 장비 하나만 고칠 때 쓴다.

### 5.2 검증 규칙 (게시 전에 실행)

| 구분 | 규칙 |
|---|---|
| 금지 | 포트 매체가 다르면 연결할 수 없다 (냉수 포트에 전원 연결 불가) |
| 금지 | 출력 → 입력 방향만 허용하고, 포트별 최대 연결 수를 넘을 수 없다 |
| 금지 | 평상시(`closed`) 연결만으로 순환이 생기면 안 된다. 타이 차단기처럼 순환을 만드는 연결은 `open`이어야 한다 |
| 경고 | 상류가 없는 부하 (전원이 없는 랙이나 항온항습기) |
| 경고 | 이중화가 기대와 다르다. 예: 듀얼 전원 랙의 A와 B 회로가 결국 같은 UPS에서 나오는 경우, N+1이어야 하는 냉동기 그룹에 단일 고장점(SPOF)이 있는 경우 |

### 5.3 변경 관리

'최초 1회'라고 해도 공사가 있으면 연결은 바뀐다. **초안 → 검증 → 게시** 순서로 진행하고, 네 기능은 **게시된 리비전만** 읽는다. 그러면 언제 무엇이 바뀌었는지가 이력으로 남는다.

## 6. 기능 4개를 그래프에서 뽑아내는 방법

| 기능 | 대상 | 그리는 방법 | 화면 전용 데이터 |
|---|---|---|---|
| **전선 단선도** | 매체가 전력인 연결 | 위 → 아래 계층. 층 번호(rank)는 소스로부터의 최장 거리로 자동 계산하고, 공조 부하와 랙은 묶음 노드로 접는다 | 수동으로 보정한 좌표 |
| **공조 흐름도** | 냉각 매체 연결 + 담당 관계(공기) | 왼쪽 → 오른쪽: 열 방출 → 냉수 생산 → 항온항습기 → 랙 | 수동으로 보정한 좌표 |
| **계통 관계** | 계통 전파 결과 + 묶음 규칙 | "UPS-A1 계통 = UPS-A1의 하류", "서버실 A 냉각 = 항온항습기에서 공조 연결만 따라 올라간 상류" | `group_rule` |
| **사이드 패널 > 연결** | 선택한 장비 | 포트별 입력 · 출력 1단계, 상류 끝까지의 경로 요약 (랙 → PDU-A3 → UPS-A1 → ATS-A → TR-A → 한전), A/B 계통이 각각 살아 있는지 | 없음 |

단선도와 흐름도는 계층을 자동으로 배치하고, 사용자가 보정한 좌표만 `view_layout`에 저장한다. 현재 [model.ts](../src/diagram/model.ts)의 고정 배치표 방식을 유지하면 장비가 하나 늘 때마다 코드를 고쳐야 한다.

## 7. 현재 코드와 비교

| 이미 있음 | 추가해야 함 |
|---|---|
| 연결 목록 하나에서 화면 4개를 계산 | 포트 (템플릿 → 인스턴스) |
| 방향 규칙, 대기 경로(`standby`), 샤프트(`via`) | `ConnKind`를 매체 / 계통 / 역할로 분리하고 계통은 전파 계산 |
| 연결 지점 (모선 · 헤더) | 담당 관계 (기류) |
| 상류 · 하류 추적, 분야를 넘는 추적 제어 ([graph.ts](../src/data/graph.ts)) | 검증 엔진, 리비전 |
| 규칙으로 뽑는 묶음 ([groups.ts](../src/data/groups.ts)) | 레이아웃 분리와 자동 배치, 편집 UI |

### 진행 순서

1. **포트와 매체 분리.** 데이터 모델만 바꾸고, 화면 4개는 지금처럼 동작해야 한다.
2. **계통 전파.** 연결마다 붙인 `sys`를 지우고 소스 장비에만 계통을 지정한다.
3. **검증 엔진.**
4. **편집 UI** (엑셀 가져오기 → 규칙 템플릿 → 도면 드래그 → 사이드 패널 순).
